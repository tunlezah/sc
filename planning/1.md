# Deliverable 1: Bluetooth A2DP Sink (Discoverable, Auto-Pairing)

## Overview / Goal

Make a Linux machine discoverable as a Bluetooth audio receiver (A2DP sink) that any phone or tablet can pair with automatically, with zero user interaction on the host side. This is the foundational subsystem that all audio features depend on.

## Technical Approach

**Primary crates:** `bluer 0.17` (high-level BlueZ bindings with `features = ["full"]`) for adapter lifecycle and device management; `zbus 4.0` (with `features = ["tokio"]`) for custom D-Bus interface implementations (Agent1, MediaEndpoint1).

**BlueZ D-Bus interfaces consumed:**

| Interface | Path | Purpose |
|-----------|------|---------|
| `org.bluez.Adapter1` | `/org/bluez/hci0` | Power on, set alias, set discoverable |
| `org.bluez.Device1` | `/org/bluez/hci0/dev_XX_XX_XX_XX_XX_XX` | Connect, disconnect, pair, trust |
| `org.bluez.AgentManager1` | `/org/bluez` | Register our pairing agent |
| `org.freedesktop.DBus.ObjectManager` | `/` | Device discovery via `InterfacesAdded` signal |

**D-Bus interfaces we implement (serve):**

| Interface | Path | Purpose |
|-----------|------|---------|
| `org.bluez.Agent1` | `/org/soundsync/agent` | Auto-accept pairing |

**Architecture pattern:** A `BluetoothManager` struct runs as a long-lived tokio task. It owns an `mpsc::Receiver<BluetoothCommand>` for commands from the web API and publishes events on the `broadcast::Sender<SystemEvent>` channel. The manager holds a `bluer::Session` and `bluer::Adapter`.

## File Structure


## Step-by-Step Implementation Tasks

1. **Create `constants.rs`** with all UUIDs (`A2DP_SINK_UUID`, `A2DP_SOURCE_UUID`, `AVRCP_TARGET`, `AVRCP_CONTROLLER`), the `AGENT_PATH` (`/org/soundsync/agent`), `BLUEZ_NODE_PREFIXES` array, and `DEVICE_PROPS_POLL` (500ms).

2. **Implement `DeviceState` and `DeviceInfo`** in `device.rs`. Include the state machine transition function `fn transition(&mut self, to: DeviceState) -> Result<(), String>` that validates legal transitions.

3. **Implement `SoundSyncAgent`** in `agent.rs` using `zbus::interface` macro. Register it on the connection at `/org/soundsync/agent`. Then call `AgentManager1.RegisterAgent(path, "NoInputNoOutput")` and `AgentManager1.RequestDefaultAgent(path)`.

4. **Implement device discovery** in `discovery.rs`. Use `bluer::Adapter::discover_devices()` which returns a stream. For each discovered device, check `device.uuids()` for A2DP UUIDs. Emit `SystemEvent::DeviceDiscovered`. Monitor `device.events()` stream for property changes.

5. **Implement `BluetoothManager`** in `manager.rs`. The main loop uses `tokio::select!` over: (a) command channel, (b) discovery stream, (c) device event streams, (d) 500ms polling fallback. On startup: power on adapter, set alias, set discoverable=true, register agent, start discovery.

6. **Wire into `main.rs`**: spawn the BluetoothManager as a tokio task.

## Testing Strategy

- Unit tests for `DeviceState` transitions: verify all valid transitions succeed and invalid ones return errors.
- Unit tests for `address_from_path` / `path_from_address`: known MAC addresses to/from D-Bus paths.
- Integration test (requires BlueZ): annotated with `#[ignore]`, powers on adapter, sets alias, verifies discoverability.

## Known Pitfalls and Mitigations

| Pitfall | Mitigation |
|---------|------------|
| `zbus 4.x` proxy builder syntax differs from 3.x | Build a minimal proof-of-concept proxy that compiles before writing application logic. |
| Lifetime errors with D-Bus proxies | Cache proxies in the `BluetoothManager` struct. Never create proxies in temporary scopes. |
| `bluer` and raw `zbus` fighting over the same D-Bus connection | Use `bluer::Session` for adapter/device operations. Create a separate `zbus::Connection::system()` for serving Agent1. |
| Agent registration fails silently | Always call `RequestDefaultAgent` after `RegisterAgent`. Log the result. |
| Device events missed during brief disconnects | Use 500ms property polling as a fallback. |

## Acceptance Criteria

1. `cargo build` succeeds with zero warnings.
2. Adapter powers on, becomes discoverable with the configured name.
3. A phone can discover the device in its Bluetooth settings.
4. Pairing completes automatically with no user interaction on the host.
5. `DeviceState` transitions are logged via `tracing` at info level.
6. All unit tests pass.
7. `SystemEvent::DeviceDiscovered` and `SystemEvent::DeviceStateChanged` events are published.
